# Task-scoped composition preflight

Before substantive UI implementation, answer these in a short paragraph or sketch
using the existing DESIGN.md and effective `contract`. Reuse established decisions;
record only a changed or missing decision in the shared document. No extra template
or minimum document length is required.

- **Decision and evidence:** What will the user compare or do? Which identities,
  values, units, denominators, status, and actions must remain visible together?
  What is supporting detail, and how is it disclosed without triggering an action?
- **Relationships:** Which peers have the same role or priority? Which anchor and
  repeated gaps should they share? Separate intentional hierarchy, section breaks,
  and selected states; symmetry is not a requirement. (DR-017, DR-018, DR-020)
- **Allocation:** Where do shared context and controls belong? Use existing
  components/tokens and assemble early. Identify avoidable repeated overhead without
  hiding required evidence, shrinking text, or manufacturing content. (DR-019)
- **Responsive behavior:** What changes at the relevant narrow and wide sizes?
  Preserve identities and readable type. For a growth contract, name its usable
  region, stable keys, reference viewport, and warranted yield. Declare an exhaustive
  finite set only when it is actually known; useful whitespace remains valid.
- **Verification:** Which existing check, app test, or human review owns each
  consequential requirement? Identify one plausible rejection and a legitimate
  alternative. Read only the applicable rule definitions/examples before authoring
  selectors or thresholds. Unknown task intent remains explicit and unassessed.

Then implement, inspect affected components and their assembled view, and run the
configured validation. A passing component does not certify the composition. Use
supported incremental review only with explicit dependency/freshness configuration;
otherwise run the full review. Inspect original-size evidence for judgments the
checks cannot establish. Do not repeat unchanged runs or reread unchanged guidance.

A review-only request does not authorize writing intent or changing boundaries.
Contract changes stay separate from application repairs; never weaken a requirement
to obtain a pass. Record only approval actually supplied by the human.
